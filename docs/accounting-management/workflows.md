# 企业账务闭环

本次沿用企业账目工作区和既有金额、凭证及组织只读边界，新增应收核销、换汇、成本分摊、服务商确认及月结。金额按企业、币种分别保存，不与 Gateway 余额或 API 计费余额合并。

## 订单：日常入口

财务后台有四个入口：订单、卡片、厂商、收款账户。一笔订单对应一次企业业务：收企业的钱 → 给企业开票 → 用 VCC 卡采购 → 收回 AI 厂商发票。

- 订单列表汇总所有企业，可按企业、状态和名称筛选；新建订单只选企业并命名。
- 订单页分收款、开票、采购、AI 发票四块，条目直接在块内添加、修改和删除，不跳转表单页。保存即生效，附件可随时补传，缺附件的条目标记“缺凭证”。
- 新条目按订单已有信息预填：付款方取企业名称，收款账户按币种选择，开票金额取未开票的收款，AI 发票厂商、账期和金额取本订单的卡消费。
- 同币种卡消费自动从本订单收款出资；币种不同时卡余额为负，在卡片行内充值补平。AI 发票生效后自动对应本订单的卡消费。四块齐全时订单自动完成；有缺项需要结束时填写原因。
- 修改：收款可改流水号、付款方、税率、日期和金额（不低于已用于卡消费的金额）；发票和 AI 发票可改全部字段，AI 发票改后重新对应卡消费；卡消费改金额、日期或卡片时，系统撤下原消费并按新内容重新入账。
- 删除：条目作废后从订单撤下，流水号、发票号和交易号可以重新录入。已用于卡消费的收款需先删除相关消费；删除卡片即停用。
- 应收、换汇、合同、支出付款、对账和月结不再出现在财务后台界面，接口和已有数据保持不变。

## 日常处理（接口保留）

财务待办覆盖草稿、缺凭证、缺已确认 AI Invoice、未收应收、待付款、未分配资金、账单待分摊、对账差异、负余额及服务商确认。各项显示剩余处理金额；分类计数覆盖全部记录，每次最多显示 200 条。选择分类会重新查询该类业务，剩余业务也可从对应企业列表处理。

原金额、累计调整、有效金额分别保留；汇总、趋势、记录主金额及客户到账金额采用有效金额。草稿支出不计入可处理的未对账数量。支出确认后进入待付款；分次付款后显示部分付款或已付款。

付款、分配默认剩余额度；已付完、已分配完的业务不继续提供无效入口。关联选项限定本企业及适用状态、币种，敏感卡片信息仍不读取。录入错误定位到字段，销售税额按币种精度预览。记录成功而附件失败时只重试附件，避免再次创建账目。

关联详情提供单据跳转、分配名称、收款核销历史和业务时间线。时间线记录操作者、请求、时间、金额及状态变化；卡片可追溯资金分配及服务商操作。CSV 按业务类型导出字段，并包含企业名称、有效金额和对账状态，不导出卡片秘密。

## 应收与收款核销

新增应收记录包含名称、参考号、到期日及可选合同、发票。确认后，一笔应收可由多笔已确认客户到账核销，一笔到账也可分摊到多笔应收。核销只改变应收已收、未收金额，不再增加资金。

核销金额同时受应收剩余金额和到账未核销金额限制。核销使用相同币种；内部换汇入金不能作为客户销售到账核销。撤销核销需填写原因；已有核销的应收和到账不能直接作废或调减至已核销金额以下。

## 换汇与资金

换汇记录原币金额、原币费用、目标币金额、明确汇率、源到账和外部参考号，凭证完成后确认。汇率定义为目标币金额／原币金额，目标币金额按目标币精度核对。

确认后锁定原币可用资金并建立独立的目标币资金来源；该资金来源不是第二笔客户销售收入。原币余额扣减原币金额和费用，目标币可用资金按实际目标金额增加。目标资金只分配到同币种有效卡片。目标资金已被占用时，禁止直接作废换汇；内部目标资金不能独立调整或作废。

## 成本分摊与付款映射

AI Invoice 可以分摊到多个已入账消费或支出，单个来源也可对应多份账单。分摊受账单未分摊金额、来源可用成本及同一实际消费的总上限约束。

跨币种分摊必须明确填写来源币金额与折算汇率，账单币金额需要按账单币种精度核对。成本折算不产生资金流，不创建换汇资金；真实换汇仍按独立换汇流程记录。

支出可以关联完全相同金额、币种的已确认 VCC 消费，表示该购买的费用映射。确认后按卡消费视为已付款，禁止再为该映射支出单独付款或调整；退款净额随来源变化。映射与原消费共用成本上限，已入账成本汇总不再次累计该映射。额外费用使用独立支出记录。

退款或作废不能使已分摊金额超过有效成本，需先核对并撤销相关分摊。账单仍有未分摊金额时保留待办，不自动填补或虚构成本。

## VCC 外部操作

VCC 分配和账务停用属于内部账务操作，不会调用服务商充值或停卡。系统记录待核对事项；财务通过服务商参考号和本卡完整凭证登记确认，分别保留账面和外部操作状态。

确实无需外部执行的事项，由管理员填写原因后标记无需执行。该标记不代表服务商已执行，也不改变原资金分配或卡片账务；原记录有误时仍需处理原业务。未处理的外部事项会阻止对应账期结账。

## 月结与历史覆盖

管理员按北京时间的已结束自然月结账。先处理该期间草稿、对账差异、账单分摊及服务商待确认事项；待收和待付本身可以跨月延续。结账生成不可覆盖的对账单版本，包含期初、本期净变动、期末及业务明细，各币种分别展示和导出。

余额追溯从账目基准及后续资金变动建立。空账套从零开始；已有账套以首次成功处理前的实际账面余额建立基准。早于该基准的历史期初余额保持未知，不能视为 0。首期在实际覆盖范围内结账时，需要管理员明确接受部分覆盖并填写说明；完全早于覆盖范围的期间不能生成推测余额。

已结期间禁止新增、确认、修改、调整和作废该期间账务；关联成本及原凭证删除也受账期限制。历史到账可在后续开放账期继续分配，历史应收可继续接受新账期的收款核销。重新开账必须由管理员填写原因；存在后续已结账期时，须从最后一个账期依次重新开账，再按时间顺序结账。旧对账单版本保留，企业只读页面只读取当前已结版本，不显示内部成本、私密字段或开账原因。

## API 扩展

管理接口仍位于 `/api/v1/admin/accounting`，沿用认证、企业事务锁、幂等和追加审计。

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| `/workbench` | GET | 企业待办、账面余额和待确认消费；支持 `reason` 分类 |
| `/receivables`、`/fx-exchanges` | GET/POST | 新增业务类型；详情、草稿修改、确认、作废沿用既有模式 |
| `/receivables/{id}/settlements` | GET/POST | 收款核销与历史 |
| `/settlements/{id}/void` | POST | 撤销核销 |
| `/fx-exchanges/{id}/allocations` | POST | 分配目标币资金 |
| `/cost-summary`、`/cost-allocations` | GET | 已入账成本、账单分摊及来源 |
| `/cost-allocations`、`/cost-allocations/{id}/void` | POST | 登记或撤销分摊 |
| `/external-actions` | GET | 服务商操作核对列表 |
| `/external-actions/{id}/confirm` | POST | 登记参考号和凭证确认 |
| `/external-actions/{id}/void` | POST | 管理员说明无需外部执行 |
| `/related/{kind}/{id}`、`/activity/{kind}/{id}` | GET | 关联业务和处理时间线 |
| `/periods`、`/periods/close`、`/periods/{id}/reopen` | GET/POST/POST | 账期列表、管理员结账和重新开账 |
| `/statements/{id}`、`/statements/{id}/export` | GET | 固定对账单及 CSV |
| `/orders` | GET/POST | 订单列表（`state=open/completed/closed`）；新建订单，可带 `transfer` 同时登记收款 |
| `/orders/{id}` | GET/PATCH | 订单详情（进度、汇总、全部记录）；修改名称和备注（带 `version`） |
| `/orders/{id}/links` | POST | 把订单外的到账、销项发票、AI Invoice 归入订单 |
| `/orders/{id}/close`、`/orders/{id}/reopen` | POST | 手动结束（需原因）、重新打开 |
| `/vcc-cards/{id}/top-ups` | POST | 卡充值（我方自有资金） |
| `/orders/{id}/entries` | POST | 在订单内新增条目（`kind` 为 transfers、invoices、vcc-cards、vcc-transactions、vendor-invoices），保存即生效 |
| `/orders/{id}/entries/{kind}/{entryId}` | PATCH/DELETE | 修改（带 `version`）或删除订单条目 |

`GET /orders` 不带 `organization_id` 时列出所有企业的订单，可用 `search` 匹配订单名或企业名。确认记录不再要求先上传凭证。发票代码和卡交易号可以留空。

新建记录可带 `order_id`；`vcc-cards`、`vcc-transactions` 必须带（退款可省略，自动沿用原消费的订单）。新增卡必须提交 `provider_card_id`（发卡平台 Card ID）和 `last_four`，不接收完整卡号；同一 Card ID 已登记时返回 409（`metadata.field=card_registered`）。

卡片的服务商、卡消费的商户、AI 发票的厂商都从厂商列表选择：卡片提交 `provider_id`（发卡服务商），消费（`CONSUME`）和 AI 发票提交 `vendor_id`（AI 厂商），后端按列表写入名称快照，忽略请求里的名称文字；停用的厂商不能新选，已选它的记录仍可保存。厂商列表接口为 `/vendors`（GET/POST）和 `/vendors/{id}`（GET/PATCH），每个厂商维护别名（小写片段，至少 3 个字符）；服务启动、新增或修改厂商时，按别名把没有厂商 ID 的历史记录自动归类，同时命中多个厂商的不归类，原文保留。

企业只读接口新增 `/api/v1/organization/accounting/periods`、`/statements/{id}` 和 `/statements/{id}/export`，范围由当前账户绑定企业确定。管理写入仍要求 `Idempotency-Key`。超额付款、月结、重新开账及外部事项豁免要求管理员；财务角色不因此获得其他后台权限。
